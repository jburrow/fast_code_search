Reference support

What the References mode (REFERENCES in the web UI, fcs refs, references=true, MCP mode: "references") finds, per language.

References are search-based, not compiler-based. While indexing, each file is parsed with tree-sitter, and the grammar’s tags query marks some names as references: call sites, type mentions, new expressions, base classes. A reference search returns the lines where the identifier appears in one of those positions. Two consequences hold for every language:

  • Names, not symbols. fcs refs parse returns every call of anything called parse, whichever class or module it belongs to. Nothing tells two functions with the same name apart.
  • Only the listed positions. A use in any other position (an import line; outside Python, a function passed as a value) is not a reference, even though a text search finds it. When references look incomplete, search the plain text as well.

A definition is never its own reference, and references are exact and case-sensitive on the identifier. Each reference is a call, type, value or attribute, and kind: filters on it (see Reference kinds).

If fcs misses a form listed as found, that is a bug; if it misses one listed as not found, that is a known gap.

Each Python reference has a kind: decorators and calls are call; annotations, base classes and exceptions type; functions and classes used as values value; attribute reads attribute. -kind:attribute leaves out property reads (see Reference kinds).

Because references are names, fcs refs get also returns every .get(…) on a dictionary, and fcs refs status_code returns reads of every attribute called status_code, whichever class it belongs to. On the repositories below, between one Python reference in ten and one in five is such a use of something else with the same name.

C and C++

No references are recorded. The C and C++ grammars’ tags queries define symbols only, so fcs refs finds nothing in .c, .h, .cpp, .cc, .hpp and the other C and C++ extensions. Use a plain or whole-word text search instead.

Ruby (.rb, .rake, .gemspec)

Calls, method calls, constants (Item.new, Util.do_thing), base classes and include Mixin are found. Ruby’s tags query is meant to skip local variables, but fcs does not apply that filter, so local variables and parameters are returned as references too (x in x = Item.new).

How complete this is

Python, against Jedi

examples/ref_oracle.rs compares the references fcs records in a repository with the ones Jedi 0.20 finds (src/check/oracle/py_refs.py): every name Jedi resolves to a function, class or property defined in the repository, other than the definition itself and import lines. A reference Jedi lists and fcs does not is missing. A reference fcs records, under the name of one of those functions or classes, where Jedi resolves the name to something else, is extra: almost always a use of something else with the same name. Where Jedi cannot resolve a name at all (an untyped receiver), neither side is counted.

CI runs it on Flask and Click (.github/workflows/ref-oracle.yml) and fails if a change misses or adds more references than that.

pip install jedi==0.20.1
python3 src/check/oracle/py_refs.py bench-corpus/flask > flask.json
cargo run --release --example ref_oracle -- --oracle flask.json
cargo run --release --example ref_oracle -- --oracle flask.json --drop-kind attribute

The report groups misses and extras by the syntax around the name, which says which row of the Python table each one is.

Other languages

There is no oracle for the other languages yet. Each form above is checked with a small file per language. To give a sense of scale, a one-off count in October 2026 took every function, method and type defined in a public repository and counted how many of its uses in code fall on a reference. The count is rough: some of those uses are not references at all (a local variable that shares a type’s name, an import line).
