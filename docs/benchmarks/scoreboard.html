fast_code_search

Scale scoreboard

The other benchmarks time the engine. This one runs the real server binary, starts and stops it, searches it over HTTP from several threads the way people do, and changes the files under it the way branch switches, formatters and builds do. Every scenario reports the same numbers, and a number over its target fails the run.

cargo build --release --bins --example scoreboard
target/release/examples/scoreboard --dir /tmp/fcs-score --files 200000 \
    --targets benches/scoreboard/targets.toml --markdown score.md --json score.json

--scenarios branch-switch,overflow runs some of them, --stream-seconds sets the stream’s length (600 by default). The tree is generated under --dir, 1,000 files to a folder, and reused by later runs (examples/support/load_tree.rs). It is shaped like the real corpus of scripts/bench/ab.sh --corpus real (Linux, LLVM, Rust, Kubernetes; 304,688 files): sizes spread like real files, with a median of 2 KB and a few over 1 MB; 55% of the files in languages fcs extracts symbols from (C, C++, Rust, Go, Python) and the rest IR, assembly, YAML and text; and contents tuned so that indexing costs, per megabyte, about what the real corpus costs. Until 2026-10-25 it was small Python files that all looked alike, which indexed several times faster than real code and hid the costs below.

The report holds numbers only: no paths, queries or file contents. That makes a run on a private tree safe to share. The server’s log and any diagnostic captures stay in --dir.

Scenarios

Each scenario starts the server on its own: from scratch for cold-build, from the saved index for the rest. Searches start at once and go on until the end. The changes start once the restart’s own check of the tree has finished (see Known gaps).

ScenarioWhat it does
cold-buildStart with no saved index; search while it builds.
warm-restartStart from the saved index; search while it loads and checks the tree.
branch-switchRewrite one file in five at once (40,000 at 200,000 files).
streamChange 200 files a second for ten minutes: rewrites, plus a new file and a removed one every 100 ms.
slow-mixEight searchers, plus a regex that reads every file every 3 s, while 50 files a second change for two minutes.
save-under-load500 files a second for two minutes, with the index saved every 5,000 applied changes.
overflowRewrite half the files at once: more events than the watcher’s queue holds (65,536), so it rescans the tree.

The searchers cycle through cheap and expensive queries (task_17_, return value, revision, default_\w+\(\), task_\d+_amber, helpers.default_cobalt) with a page of 50, as the web UI asks.

The zero targets hold at any size. The others are in benches/scoreboard/targets.toml, set at 1.3 times the worse of two runs (memory: 1.15 times), and apply only to runs with the same number of files. They are today’s numbers, not goals: they are tightened as the indexing-throughput fixes land.

In every scenario: no search turned away, refused or failed, no crash, and the check found nothing. The server answered within 0.1 s of starting in both start-up scenarios. Searches slower than 5 s wrote slow_search captures in four scenarios, with up to nine searches sharing four CPUs. overflow wrote a backlog capture in both runs, which fails the zero stall_captures target (see below).

On the earlier tree of small Python files (2026-10-23) the same machine built the index in 50 s, caught up with a branch switch in 7 s and kept search p50 under 0.7 s. Nothing got slower in between: the realistic tree holds 1.75 GB where the old one held about 40 MB (200-byte files), and its files cost what real files cost to parse.

What it found

  • Indexing throughput is the bottleneck. With realistic files the watcher applies about 200 to 300 files a second on four CPUs. A 40,000 file branch switch takes about 2.5 minutes to catch up, and rewriting half the tree takes over 8 minutes, long enough for the backlog capture to fire (changes pending for 300 s without draining). That failure is a bug report, not a target to loosen. The plan’s next items are aimed at it: the batch merge runs on one thread (most of a build’s time on the real corpus), and every removed file costs a pass over every posting list.

  • fcs check --live was cut off at 30 s. On a 200,000 file index the full check takes longer than the server’s request timeout, so it answered 504 and the scoreboard counted check problems in four scenarios. /api/check is no longer cut off at the request timeout.

  • A 4–5 s stall after every restart. An index loaded from disk keeps its unresolved imports but not the files’ import lists. At the end of the restart’s check, each of those imports got one last try, all at once and under the write lock: 368,000 imports at 200,000 files, 4 to 5 s during which every search waited. They are now tried in the same short steps as the rest of the import graph (about 250 ms each), and the slowest search after a restart fell from 4.0 s to under 1 s.

  • A backlog capture under a steady stream. The capture fired when changes had been pending for 300 s without a break, which a steady stream of edits always causes, however well the watcher keeps up. It now fires only when the watcher could not have applied what is pending in the last 10 s.

  • lock_wait counted the holding back. A search holds back for a waiting install step by design (up to 2 s, see Incremental updates), and that alone could pass the 2 s threshold. The capture now counts only the time a writer kept the search out.

Known gaps

  • The overflow scenario fails its zero target (one backlog capture) until indexing throughput improves; see above.

  • After a restart, answers say the index is incomplete for a while. Loading takes 2 to 3 s at 200,000 files. After that the server walks the tree to find files that changed while it was down, which took between 4 and 30 s here depending on the search load. Until the walk ends, every answer carries the indexing note, although only files changed since the last run can be missing (incomplete in warm-restart).

  • Changes during the restart’s check. When a large change lands while the restart’s own check still runs, the check’s steps and the watcher’s steps take turns. A search can then wait for one of each: 2.4 s was seen once, with 100,000 files rewritten 3 s after a restart. The scenarios wait for the check to finish before they change files, so this case is not covered by a target yet.

  • Lost events under a stream. One of three ten-minute streams lost events once, about 280 s in: the kernel’s inotify queue (fs.inotify.max_queued_events, 16,384 by default) overflowed. The watcher rescanned the tree and the index matched the disk again within about 15 s, with nothing missing. The cause of the sudden burst is not known yet. rescans is reported, not a target.

  • Only Linux reports memory and CPU. On other systems those columns are empty.

Where it runs

  • Nightly on GitHub (workflow “Scale scoreboard”): 200,000 files with the full ten-minute stream, against the targets. The table goes to the job summary, and the JSON and server logs are kept as an artifact.
  • On pull requests that touch locking, watching, saving, the web server or limits: 50,000 files with a two-minute stream. The zero targets apply; the time and memory targets are only for 200,000 files. A 200,000 file run takes about an hour on the realistic tree.
  • Before a release, on a large machine: a million files (--files 1000000), or your own tree with a sanitised report. The time and memory targets apply only to 200,000 files, so such a run checks the zero targets and records its numbers for comparison with the previous release.
