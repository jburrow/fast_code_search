fast_code_search

Search limits

A ranked search cannot rank what it never read, and reading every hit of a word like return in a large repository costs seconds and gigabytes. So each search collects a bounded number of matches, ranks them and shows the best. This page lists those limits, what they cost and what they hide, measured rather than guessed. Every limit that cuts a search is reported with the result (limits_hit), and every one is set in the configuration file.

How it was measured

  • Corpus: Linux, LLVM, Rust and Kubernetes together (shallow clones of their default branches, October 2026): 372,517 files, 607 MB. Common tokens have millions of hits: return 3.08M, struct 3.43M, static 1.26M.
  • Machine: a 4 vCPU cloud VM (Xeon @ 2.1 GHz, 15 GB RAM), warm page cache. Times are engine time, without HTTP. Each figure is the median of 3 runs.
  • Queries: 25, grouped by true hit count: huge (over 100k hits, 10 queries), mid (5k to 100k, 11) and small (under 5k, 4).
  • Reference: each query is first run with no limits at all, giving fcs’s own ranking of every match. A setting is judged by how much of that exhaustive top 50 its page 1 holds (top-50), and in how many queries page 1 starts with the exhaustive #1 (best first). This measures what the limits change, not whether the ranking itself is good. Ties barely affect it: at rank 50 most queries tie with 1 to 20 other hits.

To repeat it on your own code:

cargo run --release --example limits_bench -- <dir>... \
    --index /tmp/fcs-bench.idx --queries queries.txt --json out.jsonl

The first run builds and saves the index, and later runs load it. --only modes,files,budget,page picks the experiments.

Small queries reach 100% from 2,048 on. 32,768 is where quality stops improving. Going to a million adds one point and costs 26 times the time. Each collected match takes 182 to 277 bytes while the search runs, so 32,768 is about 7.5 MB per search. If all 64 permitted searches hit it at once, that is about 480 MB.

Defaults: min_match_budget = 32768, match_budget_multiplier = 8 (which only matters for pages ending past 4,096), max_match_budget = 100000. The rest of the huge-query gap is the per-file cap (below) and files with thousands of hits each.

What it costs on a small repository. The sweep above was measured on a large corpus. On tokio 1.45.0 + Django 5.2 (about 6,300 files), the same machine ran examples/corpus_bench at v0.16.2 (budget 512) and v0.17.0 (budget 32,768):

Queryv0.16.2 p50v0.17.0 p50
text, common word4.7 to 5.5 ms54 to 60 ms
text, two characters4.1 to 4.5 ms45 to 47 ms
regex, no literal3.0 to 3.6 ms100 to 108 ms

That is about ten times slower for common words and thirty times for a regex with no literal, and index builds did not change. It buys the quality above: page 1 holds the best hits instead of the first ones found. It was not named in the 0.17.0 changelog; the changelog now records it. Queries with few matches (identifiers, rare words) did not change. Whether the budget can be made cheaper when a repository has few files is an open question.

Reading order

Before 0.17, rank=full, which was auto’s choice below 5,000 candidates, read files in the order they were discovered on disk. At the same budget that order does much worse:

Order, budget 32,768huge: top-50 / bestmid: top-50 / best
best first (now)81% / 9 of 1098% / 11 of 11
discovery order (before)31% / 4 of 1091% / 10 of 11

Discovery order needed about 8 times the budget (262,144, 520 ms median) to come close. Every mode now reads best first. Sorting the candidates costs at most about 14 ms for struct’s 142k candidate files.

Files read (fast_rank_files)

Before 0.17, auto ranking switched to “fast” above 5,000 candidate files and read only the best 2,000. For common words that cost nothing, because the budget fills within the first files read. The cap mattered only for queries with many candidate files (trigram matches) but few real hits: handle_error has 8,046 candidate files and only 173 with a hit.

Neither mode was slow at any candidate count (the worst was 102 ms), so the 5,000 switch protected nothing. Default: no cap (fast_rank_files = 0). A search reads until the budget is spent or the deadline passes. A server may still set a cap, and it is reported as max_files when it bites.

A page of 1,000 gets the 100,000 budget, so it costs more. It was still under 0.3 s for 3M-hit words. MCP’s search_code used to stop at 100 hits with no way to page. Defaults: mcp.default_limit = 50, mcp.max_limit = 1000, plus offset, max_files and rank arguments.

Per-file cap (per_file_matches)

Files with more than 100 hits: return 5,685, struct 7,359, static 1,671, printf 76. The largest single file has 11,242 return hits.

Until 0.17 the cap was 100, applied to a file’s first 100 hits in file order and raised to the page end. Two things were wrong with that. Page 1 showed a busy file’s earliest hits, not its best (a file with 150 long comment lines mentioning a word before 150 short assignments to it showed the comments, score 1.2, and never the assignments, score 7.8). And because the cap grew with the page end, each offset page ranked a different sample: walking such a search by offset, as MCP tells agents to, returned 305 hits of which 155 were distinct.

Now a file keeps its best hits by score, and the cap is the same for every page in a range. Default: 1,000, the end of the range (results before 1000): a file’s 1,001st-best hit can never rank in the first 1,000 results, so the cap leaves out nothing those pages could show. From result 1000 on the cap is the page’s budget, as before. The cost is that every hit of a capped file is scored (the old cap stopped reading the file at hit 100), and a busy file uses up to 1,000 of the budget instead of 100.

Deadline

The slowest default above (a page of 1,000) took 291 ms, and a million-match budget took 2.4 s. The engine deadline, just under request_timeout_secs (30 s), only matters for regex full scans and loaded machines. Default: unchanged.

Caveats

  • One corpus, on four slow cores. Cost follows the matches collected (the budget) more than the repository size. The candidate sort grows with the number of candidate files.
  • Quality is measured against fcs’s own exhaustive ranking, not human judgement.
