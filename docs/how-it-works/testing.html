fast_code_search

How fcs is tested

fcs makes a few promises that a wrong answer breaks quietly: a search shows every match, in rank order, and finds what ripgrep finds; the index follows the disk through edits, branch switches, lost events and restarts; searches are answered while the index changes; the import graph, symbols and references are what graph support and reference support say. A missing hit looks like an empty result, not an error, so each promise has a test whose answer comes from somewhere other than fcs’s own code: ripgrep, a language’s own resolver, a deliberately naive model, or a generator that wrote every line and knows the answer.

The generated Python codebases

tests/support/pygen.rs writes packages nested up to four deep, each with an __init__.py and modules, from a seed. Modules import each other in every form graph support lists (absolute, aliased, several on one line, parenthesised lists, one to three dots, imports inside functions and under if TYPE_CHECKING:; cycles happen) and use what they import in every position reference support lists as found: calls, attribute calls, await, instantiation, obj.m(), Cls().m(), Cls.m(x), super().m(), decorators, base classes, annotations (list[C], C | None, Optional[C]), raise/except, and values in lists, dicts, keyword arguments and comparisons. Names also appear where they are not references (strings, comments, docstrings, string annotations). Every name is unique, so “the references of fn_0042” has one right answer, which the generator recorded as it wrote the line.

Before the key is trusted, Python compiles every file and grimp must draw exactly the key’s edges, line for line. Then the test rewrites the tree as another seed’s and hands the changes to the watcher in a few bursts: the incremental result must match the new key as a fresh build does.

Rank order

Everything above checks which hits a search finds and that a list is well formed; none notices when a change quietly reorders the first page, the page people read. tests/rank_snapshot.rs pins it: the first 20 hits of about a hundred searches (words, generated names, regexes, symbols, references) are kept in tests/snapshots/rank_order.txt. A ranking change is meant to move hits, so a difference is not a failure to fix but a change to accept on purpose:

FCS_UPDATE_SNAPSHOTS=1 cargo test --test rank_snapshot

and the snapshot’s diff then shows in the pull request what moved.

The web page

The contract walk’s browser leg runs scripts/e2e/web_walk.cjs with Playwright. Locally:

npm install --no-save --prefix /tmp/pw playwright@1.56.1
/tmp/pw/node_modules/.bin/playwright install chromium
NODE_PATH=/tmp/pw/node_modules FCS_REQUIRE_BROWSER=1 cargo test --release --test contract_walk

Without Playwright the leg prints a note and is skipped; CI’s Linux test job sets FCS_REQUIRE_BROWSER, so there it fails instead.

Killed at any moment

examples/chaos.rs starts the server binary on a generated tree of 20,000 files and kills it with SIGKILL, round after round, at a random moment of one of these:

KindKilled
buildduring a build from scratch, which saves a checkpoint every quarter of the tree
loadwhile it loads the saved index and checks the tree
streamwhile 300 files a second are rewritten, created and removed, and saved every 300 updates; the edits go on for a second after the kill
save0 to 20 ms after one of those saves begins (it watches for the save’s temp file every millisecond)
burstwhile the watcher installs a tenth of the files rewritten at once
shutdown0 to 20 ms after the save at shutdown (SIGTERM) begins

After each kill it starts the server again and requires: the saved index is loaded, or there was none (a kill must never leave one the next start rejects); no temp file of a killed save is left once the server answers; the server becomes ready and catches up (nothing pending, the changed files indexed as they are on disk); /api/check?all=true finds nothing; and it does not crash. The seed is printed, and --seed N replays the same kill moments; a failing round keeps its server log as failed-<round>.log.

“No index after” is a build killed before its first checkpoint: the next start builds from scratch. A build killed later loads the checkpoint and indexes the rest. CI runs 40 rounds on pull requests (seed 1) and 100 nightly (a new seed).

This tests a killed process, not a power cut: the kernel still writes out what the process wrote. A save fsyncs its file before the rename and, on Linux and macOS, the folder after it, so a power cut should leave either the old index or the new one; nothing here simulates that.

Reproducing a failure

  • proptest suites print the shrunk sequence or query that failed, which is usually enough to write a named test (the lifecycle model keeps the ones it found that way). PROPTEST_RNG_SEED=N replays a run and PROPTEST_CASES=N runs more: PROPTEST_CASES=3000 cargo test --release --test lifecycle_model.
  • FCS_PYGEN_SEEDS=1,2,3 picks the generated trees (FCS_PYGEN_PACKAGES their size) and FCS_PYGEN_KEEP=DIR writes them to DIR to look at.
  • FCS_WATCH_SEED=N replays a random watch-harness run.

On pull requests CI uses fixed seeds, so a pull request is not failed by a case it did not cause; pushes to main use new seeds each time and keep exploring. CI runs the lifecycle model 600 times, the search properties 2,000 times and the discovery oracle 1,000 times (job “fcs vs ripgrep”, which also runs the backtest on a reloaded and a watched index) and 40 generated Python trees with grimp (job “graph oracle”).

What these tests found

  • Files with no trigram (two bytes in x.py) were never searched by short queries (self-checks).
  • extra_binary_extensions was documented but rejected (self-checks).
  • The watcher indexed folders ignored by a parent’s .gitignore when something happened in them, and a restart re-indexed changed files that were now ignored (lifecycle model).
  • A file rewritten in the same timestamp tick with the same size could stay stale across a restart on coarse file systems (found while writing the lifecycle model; now covered by a unit test).
  • The watcher’s per-file ignore check disagreed with the build and with ripgrep in three ways: a rule deeper down (!a/b/ after /a) brought files back from an ignored folder; the nearest ignore file won even when a parent’s .ignore should beat a .gitignore next to the file; and rules above a nested repository were dropped inside it (discovery oracle).
  • Searches held back a fixed 250 ms for a waiting install step, too short for half-second searches: the watcher drained a backlog at 8% of its speed, not the “half speed or better” the docs claimed (lock simulation; see Incremental updates).
  • After every restart from a saved index, every search waited 4 to 5 s while the import graph’s parked imports were retried in one lock hold; a backlog diagnostic fired under steady edits the watcher kept up with (scale scoreboard).
  • A save killed half way left a temp file as large as the index, for good; a save that failed (disk full) was forgotten, so the shutdown skipped its save; a failed rename deleted the index before trying again; and a panic while reading a file during the build left it out without a word (fault points and the kill-and-restart run).
  • Earlier probes found a crash when a large file was rewritten during a search, “server unavailable” at the end of a build, and lost changes after failed reads or a panic; the fault and watch tests cover them.
